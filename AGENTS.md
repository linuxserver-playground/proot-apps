# AGENTS.md - proot-apps

## Purpose

PRoot Apps: desktop applications packaged as single-layer images, installed and run without privileges by the
`proot-apps` CLI. Imported from `linuxserver/proot-apps` with its history. It is a batch build project, not an
image repo: there is no `image.yml`, the fleet's shared workflow does not build it, and control, the hub and
the site do not list it. Its own workflows build about 130 apps, so they are capped to leave the org's 20
runner slots free for image builds.

Everything is templated on `GITHUB_REPOSITORY`: base and app images go to
`ghcr.io/linuxserver-playground/proot-apps:<name>`, the README and the release tarball's CLI defaults
(`REPLACE_USER`/`REPLACE_REPO` in `proot-apps`) follow the repository they are built in. Keep it that way: a
hard-coded org is a bug.

## Layout

| Path | What |
| --- | --- |
| `base-images/Dockerfile.<name>` | Bare distro rootfs images (`alpine-324`, `debian-trixie`, `ubuntu-resolute`...) the apps build `FROM`. They come from the distros' own images, not from the playground's s6 base images. |
| `apps/<name>/` | One app: `Dockerfile` (`FROM ghcr.io/${REPO}:<base>`, then `FROM scratch`), `package_versions.txt` written by the package bot. |
| `metadata/metadata.yml` | The app list: name, arch, category, `disabled`. The build and package-check matrices and the README come from it. |
| `proot-apps` | The CLI. `create-releases.sh` bundles it with jq, ncat (from the `bins` branch) and proot-next into the release tarballs. |
| `ci-scripts/lib.sh` | `retry_ghcr` and `retry`, vendored from `workflows/scripts/lib.sh`. Fix a bug there first, then copy it here. |
| `ci-scripts/update-packages.sh` | Package check for one app: build it, syft table into `package_versions.txt`. |
| `ci-scripts/README.template` | The README; `README.md` is generated by `template-readme.yml`, never edit it by hand. |

## Workflows

| Workflow | Trigger | What |
| --- | --- | --- |
| `build-on-commit.yml` | push to `master`, dispatch | Rebuilds the base images, then the apps that changed since the last finished `build changed` run. Dispatch inputs: `build_all`, `apps` (space-separated names), `parallel`. |
| `package-check.yml` | daily 00:00 UTC, dispatch | One job per enabled app, then `pcommit` commits changed `package_versions.txt` with `GITHUB_TOKEN` and dispatches `build-on-commit` (a push made with that token starts no workflow). Input: `parallel`. |
| `prerelease-on-commit.yml` | push to `master` (not bot commits) | Release tarballs as the prerelease `prerelease-<sha>`. |
| `publish-release.yml` | a tag other than `prerelease-*` | Release tarballs as a release, notes from `release-notes/current`. |
| `template-readme.yml` | push to `master`, dispatch | Renders `README.md`. |

Capacity rules, which every change here must keep:

- Every matrix sets `max-parallel` from the `parallel` input (the same name on every workflow that fans out;
  control will dispatch with a computed value). It defaults to 4 for push and schedule, and anything that is not
  a whole number from 1 to 16 falls back to 4. Never add a matrix without it.
- The build, package-check and README workflows each have one `concurrency` group and never cancels in progress: a newer run waits. GitHub keeps only
  one pending run per group, so the change detection diffs against the last finished `build changed` run
  (its title), not the push's `before`; a superseded push is built by the next one.
- Every registry pull, push, build or inspect runs under `retry_ghcr`; the nightly check failed only on GHCR
  429s before the cap. Plain downloads retry (`curl --retry`, `retry`).
- No secrets beyond `GITHUB_TOKEN`; no notifications (control owns them).
- It must keep working as a fork, as upstream intends: owner and repository come from `GITHUB_REPOSITORY`
  (`${REPO}` in Dockerfiles, `REPLACE_USER`/`REPLACE_REPO` in the CLI), never a literal org. A fresh fork needs
  nothing but Actions enabled and its `proot-apps` package made public.
- The repository variable `SCHEDULED_BY_CONTROL=true` turns off the package check's cron, for when control
  dispatches it with a computed `parallel`. It is not set yet: control does not dispatch it, so the cron runs.

## How to validate

```sh
actionlint
shellcheck -S warning ci-scripts/*.sh
docker build --build-arg REPO=linuxserver-playground/proot-apps -t test apps/<name>   # one app, if you changed it
```

Then dispatch the narrowest build that proves it, with a small `parallel`, after checking the org's load
(`gh run list` across `linuxserver-playground`; wait when more than about 12 jobs run):

```sh
gh workflow run build-on-commit.yml -R linuxserver-playground/proot-apps -f apps="<name> <name>" -f parallel=4
```

## Pull request rules

Disclose AI use in the description. Commit subjects are short imperative sentences without prefixes, emoji or
trailers. The bot commits (`Bot Updating ...`) keep upstream's wording, which the prerelease filter matches.
